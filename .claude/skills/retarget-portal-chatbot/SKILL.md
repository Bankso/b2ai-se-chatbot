You retarget this entire repo — agent config, docs KB, benchmarks, docs site, top-level README/CHANGELOG — from the CCKP to a different portal, the same way this repo itself was retargeted from the NF Data Portal to the CCKP (commit `72ecf6f`, "Re-target repo from NF Portal to CCKP focus"). That commit touched 59 files and is the concrete precedent for what "done" looks like — read it (`git show 72ecf6f`) before starting if you want a full worked example, though don't assume this repo's *current* state matches that commit exactly: several things (a second docs-KB source, dataset/file discovery, agent registration, a hybrid SQL+SPARQL backend design, four benchmarks instead of two) were added incrementally afterward, which is itself the lesson — retargeting isn't a single commit, it's a sequence of scoped changes you can pick up over multiple sessions. Treat `plans/implement-sparql-backend.md` and `plans/resource-search-correctness-benchmark.md` the same way even if they're still unexecuted plans rather than shipped code when you read this: they document real, hard-won lessons (a shared-graph versioning bug class, a `searchExpressions`-AND-vs-OR bug that actually shipped, an auth-token-reuse simplification) worth carrying into a new portal from day one instead of rediscovering the hard way. If they've since been executed in this repo, prefer reading the real shipped files they describe over the plan text.

**This is a large, multi-phase effort — do not attempt it end-to-end unattended.** Scope each phase with the user before starting it (which backend they actually have, whether they want a full retarget or just specific pieces), and treat live actions (crawling an external site, running paid LLM generation, deploying anything) as checkpoints to confirm, not steps to blaze through.

## Before starting: gather what you need from the user

You cannot retarget this repo from guesses. Get, at minimum:

1. **Portal name and a short slug** for it (e.g. "Cancer Complexity Knowledge Portal" / `cckp`) — used everywhere: directory names, Lambda function names, agent names, doc titles.
2. **Docs/help site URL(s)** to crawl for the KB — there may be more than one source, as CCKP has both a help site and a separate data-model reference site (`benchmark/general-help/cckpdocs_spider.py` + `mc2datamodelsdocs_spider.py`).
3. **The portal's resource entity model** — CCKP's is Dataset/Publication/Tool/Grant/EducationalResource, each a Synapse View table. A different portal will have different entity types (and may not use Synapse at all) — get the real list and, if available, the real schema/field reference docs for each.
4. **What resource backend actually exists**: a SQL-queryable table store (like CCKP's Synapse Views), a knowledge graph/SPARQL endpoint, both, or neither yet. This determines which CloudFormation template(s)/Lambda(s) are relevant — don't build both if only one exists.
5. **A real technical reference for that backend, not just user-facing help docs** — if there's a knowledge graph/SPARQL endpoint (or any non-trivial query API), ask whether the team has a spec/reference doc for it (query protocol, auth mechanism, versioning/scoping behavior). CCKP's SPARQL work (`plans/implement-sparql-backend.md`) only surfaced two load-bearing, easy-to-miss facts — the query protocol is async job-poll, not the synchronous form the NF-derived Lambda assumed, and the graph is shared across multiple portals with every historical publication loaded side-by-side (append-only, unscoped-by-default) — by reading the vendor's own reference doc, not by reading the Lambda code alone. Don't assume a new backend's protocol/auth/scoping mirrors what CCKP's Lambda already does; verify against the new portal's own source of truth.
6. **Whether individual resources can be access-restricted** (Synapse Access Requirements, or an equivalent per-object gate in whatever platform the new portal uses). If so, get at least one real, concrete example of a currently-restricted resource — this becomes the grounding fact for a dedicated redteam item (see Phase 3) instead of a generic, unverified PII-shaped guess.
7. **Deployment platform** — this repo assumes AWS Bedrock Agents + Synapse-hosted registration. If the new portal uses different infrastructure, the CloudFormation/Lambda layer needs more than a rename; say so explicitly rather than forcing the fit.
8. **Any existing demonstration plan, question bank, or vetted example-question list** the team already uses for demos or manual QA. If one exists, treat it as a first-class input to Phase 3, not an afterthought — CCKP's own benchmarks had real, non-obvious gaps (no test for AND/OR filter-combination correctness, no access-restriction-disclosure coverage, thin off-topic-decline coverage) that a team-vetted question bank surfaced immediately, faster and more reliably than synthetic generation alone. Ask for one before assuming none exists.

If any of these is unknown, ask (`AskUserQuestion` or plain conversation) before generating content — a plausible-sounding but wrong entity model or fabricated docs URL is worse than pausing to ask.

## Phase 1: Agent scaffold and backend

Reference `docs/content/docs/start-here/templates.md` — it's this repo's own living doc for reusing the CloudFormation/Lambda layer and is already written to be portal-agnostic; read and follow it rather than duplicating its instructions here. In short:

- Rename `agents/cckp-copilot/` → `agents/<slug>-copilot/` (directory, and every internal reference to `cckp-copilot` in CI/CD, README, docs).
- Rename the Lambda dirs/functions: `lambda/cckpSqlRag` → `lambda/<slug>SqlRag`, `lambda/cckpGraphRag` → `lambda/<slug>GraphRag` (only build the variant(s) matching the backend(s) that actually exist per the intake above).
- In each `cloudformation.*.yaml`: rewrite the `Instruction` parameter (the system prompt) for the new portal, replace the `KnowledgeBaseId` placeholder with the new portal's (or leave it clearly marked as a placeholder — never invent a real-looking ID), and update `SynapseAuthToken`/`SparqlEndpoint` and `TABLES`/schema references to the new entity model.
- In the SQL Lambda's `lambda_function.py`: update the `TABLES` alias map from CCKP's 5 entity types to the new portal's real ones, and check whether the dataset/file-discovery operations (`getDatasetFiles`, `getFileDetails`, `checkRestriction`) even apply — those were added specifically for Synapse-backed portals and may not transfer as-is to a different platform.
- **Verify multi-value filter-combination semantics empirically for the new backend rather than assuming CCKP's findings transfer.** CCKP's own `build_explore_url` shipped for a while with a wrong assumption (multiple `searchExpressions` entries AND together) that live-testing against production later disproved (they actually OR/union; only `facets` reliably intersect) — see the docstring in `lambda/cckpSqlRag/lambda_function.py` and `plans/combined-filter-search-expressions.md` for the full writeup. Whatever the new backend is, live-test a real multi-term filter combination against it and document the actual behavior in the new Lambda's own docstring — don't port CCKP's specific finding as if it were a general truth about search backends.
- **If a knowledge-graph/SPARQL backend is in scope, budget real design time for it — it's not a drop-in swap of the SQL variant.** Lessons from `plans/implement-sparql-backend.md`, worth checking against the new portal's real endpoint before assuming otherwise:
  - Confirm the query protocol (synchronous single-request vs. async submit-then-poll) and its response shape directly against the endpoint or its own reference doc — don't assume the previous portal's Lambda wire protocol transfers.
  - If the graph store is shared across multiple tenants/portals and/or append-only (every historical publication loaded side-by-side, nothing pruned automatically), type-anchoring to the new portal's own vocabulary is **not sufficient on its own** — queries also need named-graph/version scoping, or they silently merge stale/duplicate data across snapshots. This is exactly the kind of correctness bug that looks fine in testing (only one snapshot exists yet) and breaks the moment the source re-publishes.
  - Before provisioning a new secret for the graph endpoint's auth, check whether an existing token already wired into the stack (e.g. one used for the SQL backend's own API access) already satisfies the graph endpoint's auth requirement — CCKP's SPARQL work found the graph API's authorizer only cared about the underlying identity's team/group membership, not the token's own scopes, so the SQL Lambda's existing token worked without minting anything new.
  - If the graph Lambda has no equivalent of the SQL Lambda's redirect/URL-building tool (a knowledge graph naturally has no notion of the portal's own filtered-Explore-page URL scheme), consider the **hybrid two-Lambda pattern**: a second, narrow action group backed by the *same* SQL Lambda code, exposing *only* the URL-builder function — not full SQL query access — so the graph stays the sole data source for everything else and source-selection stays unambiguous.
  - If a redirect/URL-builder function computes something an LLM can't hand-produce (e.g. gzip+base64 encoding), have it **self-verify**: decode its own output back and compare before returning, the way `build_explore_url` does. Cheap insurance against a future encoding-step bug shipping silently.
  - Give each backend variant its own fully independent dev/prod CloudFormation stack lineage (distinct stack names, agent names, Lambda function names) rather than coupling a new/riskier variant's release cadence to an established one's — but keep the docs KB **shared** across all variants of the same portal (one `KnowledgeBaseId`, referenced by parameter, not duplicated) since it's portal-level reference material independent of which backend answers live-data queries.
  - Endpoint URLs that are CloudFormation outputs of infrastructure you don't own can change if that stack is recreated — add a short runbook note (the `aws cloudformation describe-stacks` lookup command) to the new `agents/README.md` rather than only hardcoding today's URL as a template default.
- Update each Lambda's `openapi.yaml` action-group interface and test fixtures (`tests/*.json`, `test_lambda_function.py`) to match.
- Update `.github/workflows/deploy-copilot-*.yml` for the renamed paths, including per-environment (dev/prod) parameter overrides for any value shared across backend-variant Lambdas — don't let a dev deploy of one variant silently pull in another variant's prod build artifact.

## Phase 2: Docs KB crawl

- Write a new Scrapy spider per docs source, following `benchmark/general-help/cckpdocs_spider.py` (and `mc2datamodelsdocs_spider.py` if there's a second source) as the template — same `output_markdown/`-with-source-prefix convention so multiple sources coexist without collisions.
- Confirm the target site's `robots.txt` / terms permit crawling before running it.
- Run the crawl and verify `output_markdown/*.md` is populated — this is the grounding source for everything in Phase 3.

## Phase 3: Benchmark datasets

Don't hand-roll these — this repo already has two skills purpose-built for exactly this, and they're already portal-agnostic in design (they read whatever docs/schema is actually present rather than hardcoding CCKP facts):

- **`generate-help-qa-dataset`** — generates the general-help QA dataset from whatever's in `output_markdown/`. Works as-is once Phase 2's crawl is done; no changes needed unless the new portal's directory layout differs from `benchmark/general-help/`.
- **`qa-to-kb-routing-dataset`** — converts that QA dataset into KB-routing sessions. Also works as-is, **but check `benchmark/kb-routing/kb_routing_schema.json`'s current source-label enum before assuming `DOCS`/`RAG` are still the right labels** — CCKP itself renamed `GRAPH`→`RAG` mid-project because its actual backend is SQL, not a graph; the new portal's backend shape may call for different labels again.

**If the intake turned up a real demonstration plan/question bank (see intake item 8), mine it across all benchmarks before or alongside synthetic generation, not after.** Reviewing one against CCKP's existing benchmarks (already-generated QA + KB-routing sessions + redteam config) found real, non-obvious gaps synthetic generation alone hadn't caught: no test for AND/OR filter-combination correctness, no coverage at all for access-restriction disclosure, and thin coverage of plain (non-adversarial) off-topic declines. A team's own vetted question list is higher-signal than synthetic generation because it's already been used and trusted for real demos — treat it as a first-class source:
- Lift plain off-topic/out-of-scope examples directly into `kb-routing`'s `NONE`-type sessions.
- Adapt any end-to-end demo script (overview → search → follow-up → redirect → edge case) into one long multi-turn `kb-routing` session — longer than the typical 2–5 turn session, on purpose, since it exercises turn-2+ context effects the shorter sessions don't stress as much.
- If the demo bank includes a real example of a resource with an access restriction (or equivalent per-object gate), turn it into a dedicated `redteam` vulnerability item grounded in that concrete example rather than a generic, unverified guess — see `access-restriction-disclosure` in this repo's `benchmark/redteam/redteam_config.json` for the shape (real resource ID, real restricted field, explicit distinction from PII-leakage and query-injection).
- If any red-team-style example in the bank uses a pattern not yet in `evaluate_redteam.py`'s `TECHNIQUES` dict (check the README's "Other known techniques (not yet implemented)" table first), implement it — that table exists precisely to catch this. CCKP's demo bank's first red-team example (disguising an off-topic ask as a math-problem "prerequisite") turned out to match `MathProblem`, a technique the README had already flagged as known-but-unimplemented; the demo bank was independent confirmation it was worth building.

For `benchmark/redteam/`: `redteam_config.json`'s vulnerability taxonomy (off-topic repurposing, prompt injection, scope escalation, etc.) is largely portal-agnostic, so mostly find-and-replace the portal name and entity names in each `goal`/`criteria` field rather than regenerating from scratch. Do re-read each entry afterward — a vulnerability framed around a capability the new portal's agent doesn't have (e.g. controlled-access data, a specific redirect action) needs rewording, not just renaming. **Also re-check the README's deepteam-taxonomy table's `➖` ("not applicable") rows against the new portal's real capabilities** — CCKP's table incorrectly marked `BOLA`/per-object access control as not-applicable until reviewing a real restricted-resource example showed Synapse Access Requirements are exactly that; a different portal may have its own equivalent (embargoes, tiered access, per-user permissions) worth un-excluding.

**Consider a fourth benchmark for resource-backend search/retrieval correctness.** None of the three benchmarks above test whether the agent's tool calls and answers for ordinary, good-faith resource-discovery questions are actually *correct* — `kb-routing` explicitly only grades which source was consulted, never whether the filter/join/result was right. `plans/resource-search-correctness-benchmark.md` designs this as a `benchmark/resource-search/` addition (keyword search, multi-filter AND/OR, linked-resource joins, dataset-operation status, redirect filter-shape correctness), evaluated by decoding the agent's actual tool-call parameters from Bedrock traces rather than trusting response text. If it's been built for CCKP by the time you read this, port it the same way as the other three; if not, at minimum flag the gap to the user rather than silently shipping a new portal's copilot with the same blind spot CCKP had.

For all of the above: never fabricate facts, field names, or policy details. Every claim needs to trace back to the new portal's actual crawled docs, real schema, or a real example the team provided — the same rule the two dataset-generation skills already enforce.

## Phase 4: Docs site, README, CHANGELOG

- `docs/content/docs/**` — rewrite portal-specific content (start-here guides, benchmarking-and-evaluation pages, workflow diagrams) for the new portal; `docs/hugo.toml` branding (title, base URL).
- Root `README.md` — description, links to `agents/README.md`, PHD benchmarking section, acknowledgements (credit this repo's lineage: CCKP chatbot → NF Portal Copilot, if forking from here rather than from nf-osi directly).
- `agents/README.md` — Copilot Stacks description, Synapse Registrations table (reset to empty with a note, like this repo did — **never fabricate placeholder agent IDs**), Copilot Capabilities list, Open items.
- `agents/CHANGELOG.md` — start a fresh `## <new-agent-name>` section; don't carry over CCKP's changelog history into the new portal's entry.
- Sweep for leftover `cckp`/`CCKP`/`nf-osi` references with `grep -ril "cckp" .` (excluding `.git`) once the above is done, and confirm each hit is either intentionally-preserved lineage credit or something that still needs changing.

## Phase 5: Validate before handing off

- Run each Lambda's test suite (`pytest` in `lambda/*/tests/`) after updating `TABLES`/entity references.
- Re-run the schema validation steps documented in `qa-to-kb-routing-dataset` and `generate-help-qa-dataset` on the newly generated datasets.
- Confirm every unresolved piece of infrastructure (KB ID, agent ID, SPARQL endpoint, OIDC role) is left as a **clearly marked placeholder** — this repo's convention is literal strings like `REPLACE_ME_CCKP_KB_ID` and explicit "not yet deployed" notes in READMEs — never a plausible-looking fake value that could be mistaken for real.
- Summarize what's done vs. still open (mirroring `agents/README.md`'s "Open items" pattern) and let the user review before committing or deploying anything.
