# Resource search correctness

## What this tests

[Source routing](/docs/benchmarking-and-evaluation/source-routing/) only checks whether the agent consulted the *right knowledge source* — it never checks whether the SQL/facet/join it built, or the answer it reported, was actually correct. Resource search correctness closes that gap for good-faith, non-adversarial resource-discovery questions: given a plain question and assuming the agent already routed correctly, did it build the *right* tool call and report the *right* answer?

The Bridge2AI Standards Explorer Copilot's version of this is the **resource-search benchmark** (`benchmark/resource-search/`). It exists because a real bug class — `searchExpressions`/facet AND-vs-OR confusion, and the `'Yes'`/`'No'` string-flag columns (`usedInBridge2AI`, `isOpen`) being mistaken for booleans — would pass a source-routing eval perfectly (the agent *did* call the SQL action group) while still returning a wrong filter or a wrong count. Nothing else in this repo's benchmark suite catches that.

| Benchmark | Question it answers |
|---|---|
| `kb-routing` | Did the agent consult the right *source*? Never checks whether the parameters or the answer were correct. |
| `redteam` | Under adversarial pressure, does the agent stay in scope, refuse harmful requests, and not fabricate/leak? |
| **`resource-search` (this one)** | Given a plain, good-faith question and assuming the agent already routed correctly, did it build the *right SQL/facets/D4D call* and report the *right answer*? |
| `general-help` | Docs-KB question answering only; never touches live resource data. |

## How the dataset is built

Unlike the other three benchmarks, ground truth here is computed **live against Synapse**, not authored by hand or generated by an LLM: `build_ground_truth.py` imports the deployed Lambda's own `sql_query`/`build_portal_url`/`get_d4d`/`search_d4d`/`list_d4ds`/`count_by_type` functions directly and calls them anonymously at the Lambda's pinned `TABLES` versions — the exact same code path the deployed Lambda runs. No id, name, or count in the dataset is invented.

Evaluation decodes the agent's **actual tool-call parameters** from the Bedrock trace (`enableTrace=True`), using the Lambda's own parameter-decoding functions so the grading exactly matches what the deployed Lambda sees, then checks them deterministically against each item's `expected_tool_calls` constraints (SQL text patterns, or a decoded `qw0` facet comparison for `buildPortalUrl`). A separate pass checks the final answer's facts — deterministic substring/id checks where possible, falling back to an LLM judge only for inherently free-text facts (a D4D section's narrative, a "no link found" explanation).

## Current dataset

`resource_search_dataset.json` has **42 items** across 8 categories:

| Category | Count | What it targets |
|---|---:|---|
| `keyword-lookup` | 6 | A specific standard by exact acronym resolves to the one correct `B2AI_STANDARD` id. |
| `categorical-filter` | 6 | Single-column filters, including the `'Yes'`/`'No'` string-flag bug class (`usedInBridge2AI`, `isOpen`) and the `'Is Mature'`/`'Is Not Mature'` `mature` column. |
| `multi-filter-and` | 4 | Two concepts that must **both** hold, graded as SQL `AND` / two facets — never a multi-word `SEARCH_TERM`. |
| `multi-filter-or` | 2 | Either-of intent on the **same** column, where OR is the correct semantics. |
| `linked-resource` | 7 | Cross-table joins (standard ↔ organization, dataset → org, topic → standards, org → datasets), plus a deliberate negative case (a standard with no linked organization). |
| `redirect` | 8 | Decoded `qw0` filter-shape correctness for `buildPortalUrl` search links, plus Detail Page redirects and a forbidden-shape item (a two-word `SEARCH_TERM` masquerading as an AND). |
| `d4d` | 5 | The Grand Challenge D4D sub-routine: a section fact, a cross-GC `searchD4D` comparison, an outline request, a deliberate "not covered" case, and `listD4Ds`. |
| `counts` | 4 | `countByType()` across all 7 pinned tables, plus per-category and table-total counts. |

There is no `dataset-operations`/access-restriction category (present in the CCKP-era plan this benchmark was adapted from) — every B2AI table is fully open access, so there's no restricted/external-hosting status to test.

**No B2AI agent has been deployed yet**, so `evaluate_resource_search.py` has not been run against a live agent — only its trace-parsing/grading functions have been unit-tested against a synthetic fixture (36 unit tests; 42/42 items schema-valid).

## Running it

```bash
cd benchmark/resource-search
python3 build_ground_truth.py                       # refresh ground truth after a re-pin
python3 evaluate_resource_search.py --agent-id <ID>  # all 42 items
```

See `benchmark/resource-search/README.md` for the full dataset schema, grading algorithm, and all CLI flags.
